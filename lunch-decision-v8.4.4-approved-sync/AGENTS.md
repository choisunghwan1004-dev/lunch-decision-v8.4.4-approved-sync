# 저장소 작업 지침

이 지침은 이 폴더와 하위의 점심·여행·뉴스 시스템을 수정하는 코딩 작업에 적용한다. 사용자는 시스템 변경 시 README 갱신과 커밋 관련 처리를 함께 진행하도록 요청했다. 이후의 명시적인 사용자 지시를 우선한다.

## 변경 작업을 마칠 때

1. 요청한 코드·설정·실행 파일 변경을 완료하고 기존 한국·일본 점심·여행 기능에 미치는 영향을 확인한다.
2. 같은 작업에서 `README.md`와 관련 상세 문서를 실제 구현에 맞게 갱신한다. 화면·API·DB·수집 방법·개발 환경 중 바뀐 항목, 설정값, 실행 순서와 오류 복구 방법을 반영한다.
3. `CHANGELOG.md`에 날짜, 변경 이유, 사용자가 확인할 동작, 검증 결과를 기록한다. 과거 검증 기록을 이번 실행 결과로 바꾸지 않는다.
4. 변경 범위에 맞는 의미 있는 검증을 수행한다. 문서만 바꾸면 링크·내용·차이 검사를 하고, 동작이 바뀌면 관련 테스트와 필요한 통합 검증을 진행한다. 새 변경이나 미해결 문제가 없다면 통과한 전체 검사를 반복하지 않는다.
5. 차이와 대상 파일을 검토한 뒤 해당 작업 파일만 커밋한다. 이 프로젝트에서 이미 승인된 GitHub 반영까지 진행하며, README·변경 이력·테스트·커밋에 대해 매번 재확인을 요청하지 않는다.
6. 최종 답변에 변경 내용, 실제 검증 결과와 커밋 링크를 짧게 남긴다. 사용자가 재시작·SQL 적용 등 직접 해야 할 일이 있으면 정확한 순서도 안내한다.

## 문서와 검증의 기준

- SQL을 변경하면 파일 실행 순서, 기존 DB 백업, 신규 설치와 업그레이드의 차이, 적용 확인 및 복구 방법을 README에 함께 적는다. 기존 데이터를 지우는 초기화로 업그레이드를 대신하지 않는다.
- 환경변수와 실행 파일을 바꾸면 `.env.example` 등 해당 예제와 Windows 실행 안내도 함께 확인한다. 초보자가 그대로 따라 할 수 있는 PowerShell·BAT 실행 순서를 제공한다.
- 코드는 사용자가 읽을 수 있도록 의도·흐름·DB 관계를 설명하는 한국어 주석을 충분히 작성한다. DB 관계가 바뀌면 PK/FK와 관련 설계도 갱신한다.
- 테스트 명령, 성공·실패·미실행을 구분한다. 모의 API 응답, 실제 MySQL·브라우저 검증, 실제 OpenAI·Notion 호출을 혼동하지 않는다. Linux 검증으로 Windows BAT 실행 성공을 주장하지 않는다.
- 실제로 실행하지 않은 테스트나 외부 API 호출을 성공으로 기록하지 않는다. 실패한 검증이 있으면 원인과 남은 범위를 명시한다.
- 변경된 사용법은 기존의 관련 상세 README에도 반영해 서로 모순되지 않게 한다. 과거 기록을 보존하는 구역은 현재 안내와 구분한다.

## 커밋과 GitHub 반영

- 기본 대상은 사용자가 지정한 `choisunghwan1004-dev/lunch-decision-v8.4.4-approved-sync` 저장소의 현재 작업 브랜치다. 이 작업의 승인된 대상은 `main`이다. 다른 저장소·브랜치 작업은 그 작업의 사용자 지시를 따른다.
- 원격 최신 커밋을 확인하고 그 위에 반영한다. 원격이 바뀌었으면 변경 내용을 확인해 통합하며 다른 사람의 작업을 덮어쓰거나 강제 푸시하지 않는다.
- 사용자 작업과 무관한 로컬 변경은 보존한다. 전체 파일을 일괄 스테이징하지 말고 이번 작업 파일만 선택한다.
- `.env`, API 키, 토큰, DB 비밀번호, 백업, 실제 사용자 데이터와 임시 검증 산출물을 커밋하지 않는다.
- 커밋 메시지에 변경 목적을 적고, 필요한 검증 결과를 본문에 남긴다. GitHub 반영 후 원격 커밋과 변경 파일을 확인한다.
- 인증·권한·브랜치 정책 때문에 반영할 수 없으면 로컬 결과를 보존하고 실제 차단 사유를 알린다. 원격 반영이 끝나지 않았는데 완료했다고 말하지 않는다.

이 파일은 코딩 작업의 기본 절차다. 사용자 PC의 임의 파일 변경을 감시하거나 별도의 GitHub 자동 커밋 봇을 실행하는 기능은 아니다.
